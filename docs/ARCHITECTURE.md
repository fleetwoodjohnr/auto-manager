# Architecture

```
auto-manager/
  crates/core/     auto-manager-core: all domain logic, SQLite, providers, imports, reports.
                   No Tauri dependency, so it's tested directly with `cargo test` (255 tests).
  crates/obd/      auto-manager-obd: read-only ELM327 OBD-II client (serial transport + parsers).
  src-tauri/       The desktop shell: thin #[tauri::command] adapters over the core, the
                   updater, and build.rs, which generates the IPC allow-list.
  src/             React + TypeScript UI (Vite, Tailwind v4 + Simple Suite component CSS).
  e2e/             Real-app tests through tauri-driver/WebKitWebDriver on Xvfb.
  scripts/         Release manifest, version checks, pdf.js asset copy, doc-link check.
```

## Layers

**UI (`src/`)**

- Pages live in `features/<area>/`. Shared components are in `ui/index.tsx`: the native `<dialog>` modal, badges, a virtualized sortable `DataTable`, tabs, toasts, Radix menus.
- Formatting is in `lib/format.ts`: decimal strings are rounded as strings and never converted to floats. Display-only unit conversion is in `lib/units.ts`, and the pdf.js wrapper is `lib/pdf.ts`.
- App state is a tiny zustand store (`store.ts`): route, history, toasts and an "unsaved changes" flag.
- Server state is React Query. `api/queries.ts` provides `useCmd(command, args)` and `useAction(command)`. After every change `useAction` refreshes all views of stored data, except open documents and network lookups.
- Types come from Rust through **ts-rs**: `src/api/bindings/` is generated by `npm run bindings`, and `api/types.ts` re-exports it.

**Commands (`src-tauri/src/commands/`)**

- One function per IPC call. Each validates ids, calls the core inside `Core::read` or `Core::tx` (an `IMMEDIATE` transaction), and returns `Result<T, AppError>`. Errors serialize to `{ kind, message, field }`.
- Commands run on the async runtime (`async` or `#[command(async)]`), never on the UI thread.
- `build.rs` scans the command files and writes two things: the capability file (`capabilities/main.json`, one `allow-<command>` per function plus the minimum plugin permissions) and the `generate_handler!` list. The allow-list and the handler list can't drift apart.

## Key decisions

- **Local-first, one database.** A single SQLite file with STRICT tables. IDs are UUIDv7 text, stable across backups, restores and bundles. Money and decimals are stored as TEXT and handled with `rust_decimal`.
- **Provenance over convenience.** Specifications have one row per (vehicle, key, source). The effective value is decided by source priority, and the user's corrections are separate rows. `vehicle_configuration` is a view. Nothing is hard-coded or inferred, and anything missing is shown as missing.
- **Fitment is evidence.** The engine (`fitment.rs`) decides from fitment records only. Make and model alone never make a fit. Unverified records give at most "possible". A missing vehicle detail becomes a requirement ("conditional"). See the module's doc comment for the full rules.
- **Inventory correctness lives in the database.** `CHECK (on_hand >= 0)`, `CHECK (reserved >= 0)` and `CHECK (reserved <= on_hand)` hold whatever the code does. Every change is a ledger row written in the same transaction. Undo is a compensating movement. Consuming a reservation records its movement id, so doing it twice changes nothing.
- **Search.** Triggers keep `search_docs` current, and an FTS5 trigram index over it finds substrings. Exact identifiers (VIN, SKU, part number, barcode) route straight to their record. When nothing matches, a Jaro-Winkler "did you mean" fallback runs over titles.
- **Prices explain themselves.** The engine returns the price and every step that produced it. Estimate lines store that explanation, so a later rule change doesn't silently alter old estimates.

## Sync

Optional and account-free (`crates/core/src/folder_sync.rs`). Computers share a folder that something else keeps in step: Syncthing, Dropbox, OneDrive, a network share, or a USB stick carried between them.

- **Change tracking.** Triggers on every synced table record the row's key in `sync_log` with a hybrid logical clock (milliseconds that never go backwards and move past any clock seen from another computer). Changes applied from other computers are written with the triggers switched off (`sync_clock.applying`), with the other computer's version.
- **Publishing.** Each computer writes one file, `devices/<id>.amstate`: its complete state (every row and deletion it knows, with versions), deflated and sealed with ChaCha20-Poly1305 under the group key. The key is derived with Argon2id from the passphrase and the group's salt (`auto-manager-sync.json`, which also holds a check value so a wrong passphrase is refused). Documents and photos travel as `files/<sha256>`, encrypted the same way.
- **Merging.** Syncing reads the other computers' files and keeps, per row, the highest (clock, computer id): the latest change wins, per record. Deletions are tombstones. Child rows without their own key (a document's vehicle links and page text, an OBD session's readings) travel with their parent.
- **Repairs** a row-by-row merge can't do, all deterministic so every computer reaches the same result:
  - references to rows deleted elsewhere: cleared or removed as the database's own `ON DELETE` rule would, or a protected parent (a part still stocked) is kept;
  - the same VIN, SKU, document, location, profile or category added on two computers: merged into the older row, with references moved (`sync_aliases`);
  - job, invoice and purchase-order numbers used twice: the later row takes the next number;
  - stock: levels are recomputed from the movement ledger and active reservations. If two computers took the same last units, one correction movement (with an id derived from the movements, so every computer makes the same one) brings it to zero and is reported for counting; over-reservations release the newest reservation. Costs are replayed from the ledger for items whose movements arrived;
  - a job completed on two computers: its stock movements have ids derived from the reservation or job line, so they're the same row, deducted once.

Device-local data isn't synced: settings, the audit history, cached provider answers, the bundled code reference. Every computer must run the same data version; a newer or older one is skipped with a message. **Encrypted bundles** remain for a one-way full copy.

## QuickBooks

`crates/core/src/quickbooks/`: QuickBooks → Auto Manager, one way.

- `files.rs` reads export files and `online.rs` reads QuickBooks Online. Both produce the same `QbData` (items, customers, vendors).
- `mod.rs` previews and applies it through the ordinary `inventory`, `parts`, `customers` and `suppliers` functions, in one transaction, and records `external_links` so the next import updates the same records.
- `online.rs`:
  - OAuth sign-in through a one-time `127.0.0.1` listener, with Intuit redirecting to `site/quickbooks/index.html` on GitHub Pages, which forwards to it;
  - tokens held in the OS keyring (`secrets.rs`);
  - paged GET queries through the shared `providers::http` client (HTTPS only, retries, throttling).
- The Tauri side (`src-tauri/src/commands/quickbooks.rs`) keeps the data read for a preview in memory, so what's applied is exactly what was shown.

## OBD-II

`crates/obd` is separate from the lookup system. A `Transport` trait has two implementations: the serial port, and a scripted adapter used by the tests. `Elm327::query` refuses anything except adapter setup and the reading services 01, 02, 03, 07 and 09 02. Scans are stored as sessions (`obd_sessions`, `obd_readings`).

## Adding things

- **A data provider**: see [PROVIDERS.md](PROVIDERS.md).
- **A command**: write the core function and its test, add a `#[tauri::command]` adapter in `src-tauri/src/commands/*.rs` (build.rs picks it up), then run `npm run bindings` if it adds types.
- **A schema change**: add `crates/core/migrations/00N_*.sql` and list it in `db::MIGRATIONS`. Never edit a shipped migration. The test `upgrades_each_prior_version_and_calls_backup_hook` covers every upgrade path.
